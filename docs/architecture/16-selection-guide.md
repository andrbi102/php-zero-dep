# راهنمای انتخاب معماری

> نسخه مهارت: **0.0.1** | جدول مقایسه کامل: `15-comparison-table.md` | ۱۷ سند معماری: `docs/architecture/`

## درخت انتخاب — نیاز به معماری

```
CRUD کوچک                  → MVC / Modular
قواعد کسب‌وکار پیچیده       → DDD / Hexagonal / Onion
خواندن/نوشتن نامتقارن      → CQRS
حسابرسی کامل / Time Travel → Event Sourcing (فقط Bounded Context)
همزمانی بالا               → Actor (واقع‌گرایانه: Queue + Worker)
تکرار سریع Feature         → Vertical Slice
اثرات جانبی real-time      → Event-Driven
زنجیره پردازش درخواست      → Pipeline (آسان‌ترین برای دست‌نویس)
```

## چهار پرسش تصمیم (به ترتیب بپرس)

۱) **آیا Domain قواعد پیچیده دارد؟** (محاسبه قیمت با تخفیف چندلایه، وضعیت
سفارش، اعتبارسنجی زنجیره‌ای) → بله: DDD/Hexagonal/Onion؛ نه: MVC سبک.
۲) **آیا خواندن/نوشتن نامتقارن است؟** (لیست‌های پربازدید، نوشتنِ کم) → بله: CQRS را در همان Bounded Context بررسی کن.
۳) **آیا حسابرسی کامل لازم است؟** (مالی، رضایت regulatory) → فقط آن context با Event Sourcing — نه کل سیستم.
۴) **فاز استقرار چیست؟** (هاست اشتراکی → تک‌اپلیکیشن MVC/Modular؛ سرور مستقل → گزینه‌های بیشتر) — قیدِ واقعیِ هاست، گزینه‌های روی کاغذ را محدود می‌کند.

پاسخ‌ها + ADR امضاشده توسط Council Architect (T-000-01).

## دو مثال اجرایی

**وبلاگ (پاسخ‌ها: نه/نه/نه/هاست اشتراکی):** MVC سبک با سه scaffold
(router/view/database) — ADR-0001؛ بدون بیش‌مهندسی.

**فروشگاه (قیمت‌گذاری چندلایه/لیست پربازدید/سفارش مالی حساس/سرور مستقل):**
Modular برای ماژول‌ها + CQRS فقط در ماژول سفارش + Event Sourcing فقط برای
حسابداری سفارش — سه ADR جدا؛ هسته با همان scaffolds (command-bus،
query-bus، event-store).
