# مدل سازمانی v2 — نمای کلی

> نسخه مهارت: **0.0.1** | ۵ سطح، **۷۹ نقش**، **۳۷۲ وظیفه اتمیک**، **۴۲ مجوز**،
> ۱۰ فاز مشارکت، ۶ عضو شورای ثابت، ۷ گام مشورت، ۸ گام چرخه Worker

## ایده در یک بند

هر نقش = یک Worker (زیر-ایجنت) که با قرارداد مشخص برای **یک وظیفه اتمیک**
استخدام و پس از تأیید منحل می‌شود (قاعده ۲ AGENTS.md). وظیفه اتمیک =
یک فعل، یک خروجی، یک مالک، یک DoD. این یعنی: هیچ کار «بی‌مالک» وجود
ندارد، هیچ بازخوردی «بی‌بازبین» نیست و هیچ تصمیمی «بی‌صورت‌جلسه» نمی‌ماند.

## چرا مدل سازمانی؟

خروجی PHP بدون فرایند، بدهی فنی می‌شود: کد بازبینی‌نشده، انتشار بی‌امضا،
تصمیم معماری بی‌ADR. سه ضعف کلاسیک ایجنت‌های کدنویس: (۱) همه‌چیز را
یک‌جا انجام می‌دهند و context آلوده می‌شود، (۲) سازنده و داور یک نفرند،
(۳) تصمیم‌های مهم در گفتگو گم می‌شوند. این مدل هر گام را به یک مسئول
با DoD گره می‌زند — هم‌راستا با چرخه «plan → test → implement → review →
verify → remember → improve» (SPEC بخش ۱۵، ECC).

**به زبان عملی:** وقتی مهارت فعال می‌شود، ایجنتِ اصلی نقش «کارفرما» را
دارد: نیاز را تحلیل می‌کند، برای هر وظیفه اتمیک یک Worker با قرارداد
استخدام می‌کند، خروجی را می‌گیرد، بازبینی می‌طلبد و در درگاه‌های شورا
تصمیم می‌گیرد. شمارش‌ها (۷۹/۳۷۲/۴۲) از `RULES.json` تولید می‌شوند و
`scripts/verify_org.py` گارد رگرسیون آنهاست (درس L-001).

## نکته‌های اجرایی برای ایجنت

1. **شمارش‌ها را هرگز هاردکد نکن** — از `RULES.json` بخوان؛ `verify_org.py`
   پیش از هر انتشار اجرا شود.
2. **نقش‌های فاز جاری فقط** — فعال‌سازی نقشِ فاز دیگر، نقض قاعده ۱
   AGENTS.md است.
3. **قرارداد بدون DoD نامعتبر است** — DoD باید با «بله/نه» قابل قضاوت باشد.
4. **شورا مقام بالاترِ وتوی امنیتی ندارد** — هیچ فشاری وتوی T-001 را
   نمی‌شکند (قاعده ۵ AGENTS.md).
