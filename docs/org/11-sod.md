# تفکیک وظایف (SoD-1..5)

> نسخه مهارت: **0.0.1** | گارد خودکار: scripts/verify_org.py

## پنج قاعده

- **SoD-1:** هیچ Worker هم‌زمان write-X و approve-X ندارد
- **SoD-2:** approve-release نیازمند ۲ امضا (Release Manager + ۱ شورا)
- **SoD-3:** veto-security فقط توسط Council Security یا Security Engineer
- **SoD-4:** exec-migration فقط توسط Database Lead یا DB Migration Specialist
- **SoD-5:** Code Reviewer نمی‌تواند نویسنده همان کد باشد

## چرا SoD؟ — منطق هر قاعده

| قاعده | خطرِ بدونِ آن | مثال واقعی |
|-------|----------------|-------------|
| SoD-1 | خودتأییدی: سازنده همان را تأیید می‌کند | کد ناقصِ «تأیید‌شده» توسط نویسنده‌اش |
| SoD-2 | انتشار تک‌امضا | انتشار عجولانه بدون داور دوم |
| SoD-3 | وتوی امنیتی توسط غیرمتخصص — دو جهت: ابطال بی‌دلیل یا عبور خطرناک | مجری که وتو را «توصیه» تلقی می‌کند |
| SoD-4 | مهاجرت دیتابیس توسط غیرمتخصص | کوئری DROP در محیط production |
| SoD-5 | بازبینیِ خودِ نویسنده | هم‌دلی با باگِ خودساخته |

## استثنای مستند — release

طبق مشورت C-001 (consultation/log/2026-11-25-sod-release-exception.md):
Release Manager (T-005) هم `write-release` و هم `approve-release` دارد؛
چون امضای approve-release طبق SoD-2 **دولایه** است (RM + ۱ عضو شورا)،
خودتأییدی ساختاراً ناممکن است. هم‌امضای الزامی: حداقل یک عضو شورا
دارای approve-release (در پیاده‌سازی فعلی: Council Architect).
این استثنا در `scripts/verify_org.py` به‌صورت گارد کد شده است.

## نمونه اجرایی — SoD-5 در عمل

**صحنه:** Core Developer (T-048) فایل اتولودر را نوشته و برای صرفه‌جویی
پیشنهاد می‌دهد «خودم بازبینی کنم، سرعت‌تر است».

**برخورد:** نقض SoD-5 — بازبینی با Code Reviewer (T-074) است، حتی اگر
کندتر باشد. اگر T-074 در دسترس نیست (پروفایل solo، شلوغی صف)، بازبینی
به سرپرست سطح ۱ (Chief Architect) ارجاع می‌شود — اما هرگز به نویسنده برنمی‌گردد.

**رکورد:** این تعویض در consultation/ ثبت می‌شود و DoD بازبینی همان
می‌ماند (یافته‌ها با severity، تأیید صریح).

## گارد ماشینی و نقش ایجنت

- `python3 scripts/verify_org.py` — SoD-1..5 را به‌همراه شمارش‌ها راستی‌آزمایی
  می‌کند؛ خروجی قرمز یعنی انتشار ممنوع (درگاه F9/F10).
- ایجنت هنگام پر کردن بخش Authority هر قرارداد (`scaffolds/workers/_template.md`)
  باید SoD را ذهنی چک کند: «آیا این Worker چیزی را می‌سازد و همان را
  تأیید می‌کند؟» — اگر بله، یا مجوز تأیید را حذف کن یا مشورت ثبت کن.
- **استثنا فقط با مشورت + مستندسازی + گارد:** الگوی پذیرش استثنا =
  همان سه‌گانه C-001 (مشورت → سند در همین فایل → کد در verify_org.py).
