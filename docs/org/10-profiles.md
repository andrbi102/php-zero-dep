# پروفایل‌های اجرا (full / solo)

> نسخه مهارت: **0.0.1** | منبع: RULES.json → org_model.profiles

## دو پروفایل

| پروفایل | فازها | Worker هم‌زمان | مناسب برای |
|---------|-------|----------------|------------|
| **full** | F1..F10 (همه) | بدون سقف | پروژه بزرگ — کل مدل شورا |
| **solo** | F1, F2, F4, F5, F6, F9, F10 | حداکثر ۷ | پروژه کوچک — یک معماری + Security Reviewer + Code Reviewer؛ F3/F7/F8 درون‌سازی و تأیید شورا دسته‌ای |

قاعده ۱۴ پرامپت اصلی: فقط نقش‌های لازم فاز جاری به‌صورت Worker فعال
می‌شوند — در solo، امضاهای شورا به‌صورت batch در F9/F10 جمع می‌شوند؛
قواعد وتو (به‌ویژه امنیت) در هیچ پروفایلی تعطیل نمی‌شود.

## انتخاب پروفایل — پرسش‌های تصمیم

1. **دامنه:** یک دامنه کسب‌وکار و یک مخزن؟ → solo. چند دامنه/سرویس مستقل؟ → full.
2. **تیم:** کاربرِ واحد و ایجنتِ واحد؟ → solo. چند جریان کاری موازی؟ → full.
3. **ریسک:** داده حساس/پرداخت/کاربر زیاد؟ حتی با پروژه کوچک، F7 جداگانه
   ارزش دارد → full را در نظر بگیر (یا در solo، چک‌لیست F7 را صریح در F5 اجرا کن).
4. **مستندسازی:** محصولِ چند-کاربره/متن‌باز؟ → full (F8 مستقل).

**شروع ساده:** مطمئن نیستی؟ `solo` — ارتقا در هر مرزِ فاز ممکن است و
هزینه‌اش یک ADR است (نمونه در `SKILL.md` بخش ۸).

## solo چه چیزی را «حذف نمی‌کند»

این جدول مهم‌ترین نکته پروفایل solo است — سه فازِ غایب، تعطیل نمی‌شوند:

| فاز غایب از solo | به چه شکل برقرار می‌ماند |
|-------------------|---------------------------|
| F3 تأیید طراحی | طراحی در F2 توسط همان معمار انجام و در F9/F10 با امضای دسته‌ای شورا تأیید می‌شود |
| F7 بازبینی امنیتی | چک‌لیست امنیتی درون F5 (بازبینی کد) اجرا؛ وتوی امنیتی همچنان مطلق |
| F8 مستندسازی | README محصول و محدودیت‌ها درون F4/F9 تولید می‌شود |

## نمونه اجرایی — مقایسه دو پروژه

**وبلاگ شخصی (solo):** F1 (یک Worker معمار) → F2 (طراحی + ADR) → F4 (تا ۷
Worker: هسته، روتر، فرانت، مهاجرت) → F5 (بازبین + چک‌لیست امنیتی) → F6
(تست) → F9 (RM نسخه/CHANGELOG) → F10 (انتشار با ۵ امضای دسته‌ای).
جمع: کمینه Worker، امضاها یک‌جا، وتوها برقرار.

**فروشگاه اینترنتی (full):** هر ۱۰ فاز جداگانه؛ F3 با حداقل ۵ حضور سطح ۰؛
F7 امضای `security-signoff.md` مستقل؛ F8 مستندسازی تیمی؛ انتشار با ۵
امضا در جلسه رسمی — ثبت‌شده در `council-log.md`.

## نکته‌های اجرایی

- **سقف ۷ در solo:** صف وظایف را بچین؛ Workerهای تمام‌شده پیش از استخدام
  جدید منحل می‌شوند (قاعده ۲ AGENTS.md) — سقف، انگیزه انحلال به‌موقع است.
- **ارتقا mid-flight:** فاز جاری را تمام کن، فازهای درون‌سازی‌شده را صریح
  باز کن (مثلاً F7 مستقل برای پس‌مانده ریسک)، ثبت در ADR.
- **profile در RULES.json:** منبع رسمی فازها/سقف؛ متن، فقط نمای آن است.
